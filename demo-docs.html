How Sakni auth works

edited 2h ago340 words~2 min read

The flow starts when the user visits the deployed site. Supabase Auth checks for an existing session token in localStorage.

Sign-in path

  1. If no session: render the magic-link form on the auth screen.
  2. User types email, clicks Send link.
  3. We call supabase.auth.signInWithOtp({ email, options: { emailRedirectTo } }).
  4. Email arrives via Resend SMTP (config in Supabase).
  5. User clicks the link → returns to solo-ideas.vercel.app/?code=....

Token exchange

The Supabase JS client auto-detects the ?code param via detectSessionInUrl: true and exchanges it for an access + refresh token pair. Both are stored in localStorage.

Refresh tokens rotate. Access tokens last ~1 hour. The SDK refreshes silently in the background.

RLS

All queries are filtered by auth.uid() = user_id via Row Level Security policies. The anon key in config.js is public-safe — RLS is what actually protects the data.

What you get: Click a doc → opens this big reader pane. Markdown rendered properly (headings, code blocks, lists, blockquotes). Edit swaps to a textarea, Archive moves it, × closes. Word count, read time, and "edited Xh ago" up top.

The full picture: Title + body separation gives the list its scannable shape. Pin replaces the irrelevant status circle. Click any row → reader view opens with full markdown rendering, edit toggle, and meta (edited / words / read time). All three pieces compound — none of them does much alone, but together they make Docs feel like a real notes app.

Option 1 — Title + body

First markdown line = title

Effort

  • Small. Pure client-side parsing — no schema change.

Strong

  • Scannable list. Title pops, preview hints at content.
  • No new field to fill in — write naturally.
  • Auto-meta (word count, last edited) for free.

Weak

  • If you forget to start with #, the first line becomes the title regardless. (Fine — that's how the brain works anyway.)

Option 2 — Reader view

Click row → full-screen modal

Effort

  • Medium. New modal component + edit toggle + word-count helper.

Strong

  • Long docs are actually readable — proper line height, headings, code blocks.
  • Clear edit ↔ read distinction.
  • Meta strip (edited, words, read time) signals freshness + scope.

Weak

  • One extra click to read (vs inline).
  • Bigger UI surface to maintain.

Option 3 — Pin instead of status

Docs aren't todos

Effort

  • Small. Add pinned boolean to items, swap UI for kind=doc.

Strong

  • Matches how docs actually behave — they're reference, not work.
  • Most-used docs surface to the top automatically.
  • Status cycle stays for Notes/Ideas/Tasks where it makes sense.

Weak

  • Schema change (small, additive — same migration pattern as before).
  • Slightly different mental model per tab — but that's the point.

All three combined ⭐

Strongly recommended

Why bundle

  • Each one alone is okay. Together they transform Docs.
  • Title-only list (#1) is what makes the reader view (#2) worth opening.
  • Pin (#3) replaces a status that's meaningless for reference material.

Effort

  • One milestone — call it M3.5. Single migration + one focused PR.

Out of scope here (next round)

  • Code-block syntax highlighting.
  • [[Sakni]] wiki-style cross-project links.
  • Card grid view (vs row list) for Docs.
How to use: click each option above. Reply with the option number — 1, 2, 3, or all — and I'll ship M3.5. AI suggestions (M4) is still deferred until you're ready to chat through the cadence/UX.
